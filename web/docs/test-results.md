# Turnline 验证记录

## Web 轮次与播报优化

本机 Intel Core i5-8260U，Python 3.13.15，sherpa-onnx 2.0.3，使用 Playwright Chromium、虚拟麦克风和真实语音模型。演示后端以均衡档位和流式播报跑了 20 轮热态短问答。

| 指标（毫秒） | P50 | P95 | 最大值 |
| --- | ---: | ---: | ---: |
| 停说到可闻首声 | 904.5 | 939 | 948 |
| 停说到提交 | 480 | 480 | 480 |
| 开口到首条字幕 | 774.5 | 791 | 798 |
| 提交到可闻首声 | 406.5 | 439 | 457 |

演示延迟通过 1100/1500 毫秒的 P50/P95 门槛，首条字幕通过 1200 毫秒的 P95 门槛。旧记录从断句事件算起，并以播放缓冲开始为终点，新口径包含断句等待并使用有声 PCM 的设备播放时间。

同机并行运行另一套浏览器和语音模型做回声长跑时，停说到可闻首声的 P50/P95 曾升至约 1886/3735 毫秒。这个场景用于记录 CPU 争用对断句与合成的影响。\n\n用真实 Pipiclaw 的本地中转做了一轮虚拟麦克风回归。通话开始时预建会话，语音提交后收到播报，刷新后恢复同一份对话。该轮停说到首声 4139 毫秒，其中停说到提交 480 毫秒，请求到首字 3327 毫秒。

句中停顿抽样采用约 0.9 秒间隔，20 轮全部合并为一次提交。浏览器回归覆盖超过 20 秒的连续口述、默认半双工在播报末尾接话、语音通道断开约 5 秒后恢复以及会话模式下续说串行提交。

20 次可选插话的首次压低和首次暂停 P95 分别为 147 毫秒和 275 毫秒。浏览器先暂停并保留播放头，服务端的转写用于确认停播或恢复。\n\n可选开口打断在 10 分钟的 −20 dB 数字回声注入中完成 123 个播报回合，误打断和额外提交均为 0。虚拟麦克风路径验证了回声文本过滤，外放 AEC、真实耳机、蓝牙和手机还需要实机验收。复现命令及计时口径见[测试手册](testing.md)。

## 通话指令、插话和后台回执复验

在本机已运行的 Pipiclaw 上，使用新的通话指令测了五轮 HTTP 流式请求，其中一轮要求用工具计算。表中延迟从客户端发送请求开始，单位为毫秒。确认等待是第一段完整句出现到该消息的正文类别确认。

| 样本 | 首字 | 首段完整句 | 正文确认 | 确认等待 |
| --- | ---: | ---: | ---: | ---: |
| 冰为什么上浮 | 2121 | 2548 | 2665 | 117 |
| 分钱计算 | 2254 | 2255 | 2359 | 104 |
| 下雨后的首要动作 | 1022 | 1251 | 1376 | 125 |
| 用户说先等等 | 1049 | 1221 | 1348 | 127 |
| 用工具计算 | 3404 | 3453 | 3591 | 138 |

五轮的后端排队为 0–1 毫秒。即时播报在这组样本中最多提前约 138 毫秒拿到首段文本。默认继续等正文确认。这组测量只覆盖本机后端和短回复，音频合成及设备输出另计。

本机浏览器联调用真实 Pipiclaw 创建了一个简单后台计算任务，确认了正文语音、后台结果的文字和短播报，以及挂断后同一会话发送普通文字。浏览器离线回归用虚拟麦克风验证了附和后继续播、有效插话后换轮、普通 SSE 与会话更新去重，以及挂断后会话更新只显示文字。Kokoro 自己合成的「嗯」可被 SenseVoice 误识为其他词，Kokoro 兼容用例仅对这一条转写使用固定文本，保留真实 VAD 和播放链路。默认 Matcha 的附和用例走真实转写。实体耳机与外放还需现场验证。

## 必须修

### 1. 词表外的英文被静默丢掉

影响：说或让助手读出「Kubernetes」时，听众听不到这个名字，界面也不报错。数字和词表内英文是正常的。

复现：启动 `uv run python server.py --host 127.0.0.1 --port 4173`，按手册第 2 节合成 `mixed`（文本是「请记住，版本是二点五，名字叫 Kubernetes。」，`speaker: 3`）。服务日志出现：

```text
OOV word skipped: 'Kubernetes'
```

把合成结果送回 `/speech/listen`，转写是「请记住版本是2.5，名字叫。」对照：

| 文本 | 回环转写 |
| --- | --- |
| 请记住，版本是二点五，名字叫 Kubernetes。 | 请记住版本是2.5，名字叫。 |
| 名字叫 hello。 | 名字叫hello。 |
| 名字叫 kubernetes。 | 名字叫。 |

`hello` 在 `models/kokoro-int8-multi-lang-v1_1/lexicon-us-en.txt` 里。`Kubernetes` / `kubernetes` 都不在。`speech.py` 的 `SpeechModels.synthesize` 把文本直接交给 `voice.generate`。sherpa-onnx 的 Kokoro 在 `TokenizeFromLexiconStr` 里跳过词表外单词，仍然返回一段有限、非静音的 PCM，所以 `synthesize` 里的空音频检查不会触发。

期望：这句里的英文专名要被读出来。大小写都不应该整词消失。修完后用同一句做合成再识别，转写里要能看出 Kubernetes（允许大小写、空格或逐字母拼读的差异）。词表内的 `hello` 仍要能读。失败时界面要有可理解的错误，不能再静默返回少了词的音频。

不要做的事：不要为了消掉日志把未知词换成空字符串。不要放宽「PCM 必须有限且非静音」的检查。

### 2. 语音活动检测裁掉起音，官方样本首词变错

影响：`models/.../test_wavs/zh.wav` 经正式收音 WebSocket 后，第一个词从「开饭」变成「派饭」。时间「早上 9 点至下午 5 点」还在，所以手册第 3 节的断言能通过，但首词是错的，而且是 Turnline 的切段造成的。

证据：同一文件、`use_itn=True`。

| 输入 | 转写 |
| --- | --- |
| 整段 WAV，不经过 VAD | 开饭时间早上9点至下午5点。 |
| `/speech/listen` 按手册第 3 节送入 | 派饭时间早上9点至下午5点。 |
| VAD 切出的片段（与文件中一段样本逐点相同） | 派饭时间早上9点至下午5点。 |
| 在该片段前补回 16 ms 原始音频 | 开饭时间早上9点至下午5点。 |

文件能量大约从 0.720 秒开始。`ListeningTurn.accept` 交出去的片段从文件的第 12064 个样本开始，也就是 0.754 秒，晚了约 34 ms（544 个样本），长度 69632 样本（4.352 秒）。片段和文件对应区间的最大绝对差是 0，不是缓冲被覆盖。`speech.py` 里 `segments.append(self.detector.front.samples)` 得到的是一份普通 list，`pop()` 之后内容不变。

上游 sherpa 文档里，这份 WAV 在不开 ITN 时是「开饭时间早上九点至下午五点」，开 ITN 的示例是「开放时间早上9点至下午5点。」本机整段识别停在「开饭」而不是文档里的「开放」，那是当前 sherpa-onnx 2.0.3 的模型输出。修的目标是让收音路径不要比整段识别更差：首词应是「开饭」或「开放」，不能是「派饭」。补到 48 ms 以上时，模型会在「开饭」和「开放」之间晃，两种都保留了原意。

相关代码：`speech.py` 的 `ListeningTurn`。Silero 参数是阈值 0.55、最短语音 0.18 秒、窗口 512。窗口大约 32 ms，和被裁掉的 34 ms 一致。检测器返回的是触发之后的片段，前面没有预留。

期望：手册第 3 节的 `basic`、`recorded-zh`、`silence` 三条仍通过，并且 `recorded-zh` 的转写包含「开饭」或「开放」，同时仍包含早上、下午、9 点（或九点）和 5 点（或五点）。`basic` 的整句「你好，今天天气怎么样？」不要因为多留的静音被切碎或丢字。两秒空白仍然没有任何 `speech-start`。

不要做的事：不要把阈值降到会让静音或 0.3 秒句中停顿误触发。当前 500 ms 阈值下，合成音中间插入 0.3 秒空白仍是一段，插入 0.9 秒会分成两段，这是设置本身，不是这个缺陷。

## 可以修，但有明确边界

### 3. 即时播报会先读出后来才标成进度的句子

本地演示、播报模式选「分句即时播报」、发送「告诉我进度。」时，发给 `/speech/synthesize` 的文本是：

```text
正在检查。
处理完了。
详细结果可以在屏幕上看。
```

「只播报确认后的正文」时只有后两句。界面上「正在检查。」最终会标成进度。这和 README 里对 Pipiclaw 的说明一致：有的进度要等整段结束才改类别，即时模式可能先读出来。

原因在两条路径叠在一起：

- `server.py` 的 `demo` 在 `response.output_item.added` 时把 `phase` 写成 `final_answer`，到 `response.output_item.done` 才改成调用方传入的 `commentary`。
- `public/app.js` 的 `processEvent` 在 `reading === 'live'` 时，每个 delta 都调用 `drain`。`drain` 只在 `entry.phase === 'commentary'` 时跳过。进度句带句号，会在阶段还是 `final_answer` 时就被送去合成。

期望：确认模式的合成列表保持现在这两句，不能把「正在检查。」加进去，也不能漏掉正文。若要让本地演示的即时模式也不读进度，应在 `output_item.added` 就带上真实的 `commentary`，让现有的 `drain` 跳过它。Pipiclaw 若仍在 item 完成之后才把正文改成进度，客户端无法提前知道。不要为了这种情况让确认模式等完整轮结束，也不要把即时模式改成等所有 delta 结束再开口。

## 性能：功能通过，没有达到体验目标

热态短问答的首声目标是中位数 1.5 秒。这次没有达到。瓶颈在 Kokoro，不在识别。一句要合成完才开始播，而这台 CPU 上生成比音频更慢。

没有单独要求修延迟。若要动合成速度，不要改识别阈值或断句时间来「显得更快」。

- 耳机和外放。没有测插话成功率、把自己的播报当成人声、以及插话时吞掉前几个字。
- 真人在句中停顿和说完后停顿。只有上面的合成音插入空白。
- 用扬声器听 `basic.wav` 和 `mixed.wav`。英文漏读靠的是 Kokoro 日志和识别回环，不是人耳。
- 浏览器的「离线」开关。对 `127.0.0.1` 模拟离线 8 秒，已建立的收音 WebSocket 仍显示「正在聆听」。不要把这个当成缺陷去改页面，除非先证明服务真的断开了而页面没有提示。停进程的路径已经有提示。

## 不要当成缺陷去改

- 手册第 3 节允许标点、空格和数字写法不同。`zh.wav` 写成「9点」而不是「九点」是符合的。要修的是「派饭」。
- 整段识别是「开饭」而文档示例是「开放」，在补上起音之后可以保留，两种都算过。
- 500 ms 断句把 0.9 秒的句中停顿切成两段，是这个档位的行为。不要为了这一条把默认停顿改长。
- `/speech/synthesize` 拒绝超过 128 字的单次请求。正常播报先用 `splitSpeech` 分成大约不超过 80 字的短语，用户路径没有碰到这个上限。
- 演示后端在打断瞬间已经发出的一个增量，可以留在文字里。验收标准是旧音频停止，迟到的最后一句不再播放。
